# Fione v2 設計書(ドラフト)

日付: 2026-10-24 / 状態: ドラフト(ユーザーの回答を反映済み。全体の承認待ち)

「**[判断]**」は設計者の判断で、ユーザーの合意ではありません。「**[ユーザー]**」はユーザーの発言です。

## 1. 目的と背景

Fione は「ブラウザだけで、CSV から予測モデルを作り、予測 API まで出せる、Docker で 1 コマンド起動の AutoML サーバー」。想定ユーザーは ML 未経験者と、ベースラインを素早く得たい専門家。

現状(v1)は Fess(管理画面の枠組み・認証)と H2O(AutoML エンジン)に強く依存し、開発が難しい。**[ユーザー]** コンセプトと「今までできていたこと」は維持し、実装は変えてよい。Java から Python に移し、Fess・H2O に依存せず、Docker で提供する。fione-serving も Python 化してよい。H2O のような自動モデル構築に加え、LLM による EDA・モデル作成の支援を入れたい。使い勝手とわかりやすさを最優先し、精度は大幅に劣化しなければよい。

### 調査でわかった v1 の実態(コード確認済み)
- Fess は検索・クロール・スケジューラを使っていない。使っているのは管理画面の枠組み、ログイン/ロール、ストレージ設定、i18n、ProcessHelper のみ。外す作業は検索の再実装ではなく、UI と認証の作り直し。Elasticsearch は不要になる。
- 永続データは全て S3(MinIO)上の JSON とファイル(`<bucket>/fione/<projectId>/...`)。独自の ES インデックスはない。
- ジョブは生の `new Thread` と H2O Jobs API のポーリング。Fess のスケジューラは未使用。
- 現行の Serving 配布は「Dockerfile + fione-serving.jar + model.zip」の ZIP で、ユーザーが `docker build` する。
- MinIO は 2026-04-25 にリポジトリがアーカイブされ、保守終了(ライセンスは AGPLv3)。

## 2. 検証で判明した事実

### 2.1 H2O の MOJO 出力が OSS 版で閉じている
H2O 3.46.0.12 では、プレーンな GBM でも `save_mojo` が失敗し(`MOJO export requires H2O-3 Secure`)、REST の `GET /3/Models/{id}/mojo` もサーバー側で HTTP 412 で拒否される(「H2O-3 SECURE REQUIRED - MOJO export is blocked」)。現行の Serving(MOJO 前提)は、最近の OSS 版 H2O では成立しない。H2O からの脱却は、開発のしやすさだけでなく、機能維持のためにも必要。

### 2.2 エンジン比較(スパイク。使い捨てコード、2 シード平均、同一マシン 16 コア)
自作 = LightGBM / XGBoost / CatBoost / ExtraTrees を Optuna で探索し、OOF 予測に対する Caruana 法でアンサンブル。時間予算は iris・Titanic が 30 秒、Adult・California が 120 秒。

| データ | システム | テスト精度 | 学習時間 | 成果物サイズ |
|---|---|---|---|---|
| Adult(2 値) | 自作 | acc 0.8764 / AUC 0.9302 / logloss 0.2738 | 140 秒 | 761MB |
| | AutoGluon | 0.8756 / 0.9304 / 0.2728 | 49 秒 | 1235MB |
| | H2O | 0.8746 / 0.9293 / 0.2756 | 127 秒 | 36MB(モデル保存) |
| California(回帰) | 自作 | RMSE 0.4335 / R2 0.8575 | 122 秒 | 776MB |
| | AutoGluon | 0.4311 / 0.8591 | 108 秒 | 773MB |
| | H2O | 0.4387 / 0.8541 | 126 秒 | 94MB |
| Titanic | 自作 | acc 0.8171 / AUC 0.8480 | 28 秒 | 20MB |
| | AutoGluon | 0.8140 / 0.8434 | 20 秒 | 43MB |
| | H2O | 未計測(スパイクのスクリプト不具合) | - | - |
| iris | 自作 | acc 0.9868 / logloss 0.1066 | 29 秒 | 10MB |
| | AutoGluon | 0.9737 / 0.0769 | 15 秒 | 7MB |
| | H2O | 1.0000 / 0.0455 | 36 秒 | - |

読み取れること:
- 自作は AutoGluon・H2O と実用上同等の精度。**大幅な劣化はない**(iris・Titanic は行数が少なく、2 シードでは差が誤差の範囲)。
- **時間予算を守れていない**(自作は 120 秒指定で 135〜144 秒)。AutoGluon は予算内で早く終わる。→ 要件 5.1。
- **成果物が大きい**。全ファミリー・全 fold のモデルを保存しているため。→ 要件 5.2。
- 注意: 精度は最終テストセット 1 回分の比較で、データセットも 4 つのみ。エンジンの優劣を断定する根拠ではない。H2O の成果物サイズは MOJO ではなく H2O 独自形式の値。

## 3. ゴール / 非ゴール / アンチゴール

**ゴール**
- G1. v1 でできたことを再現する(7 章の一覧)。
- G2. Fess・H2O・MinIO に依存しない。`docker compose up` 1 回で起動する。
- G3. EDA・モデル作成が v1 以上にできる。
- G4. LLM アシスタントが EDA・学習設定・結果解釈を支援する。LLM なしでも全機能が使える。
- G5. 使い勝手とわかりやすさを最優先する。

**非ゴール**
- v1 の MinIO 上のプロジェクト・H2O モデルの移行(**[判断]** H2O のバイナリモデルは移行不可。v1 のデータセット CSV の取り込みも Phase 1 の対象外とし、必要なら CSV を手動でアップロードする)。
- 検索機能・Fess 連携(v1 ドキュメントでも「未統合」)。
- 画像・テキスト・時系列などの表形式以外の AutoML(初期)。

**アンチゴール(技術的には動いても失敗)**
- 特定の AutoML ライブラリに再び強く依存して、開発が止まる。
- 設定項目だらけで、ML 未経験者が使えない。
- LLM がデータを黙って外部に送る。LLM が生成したコードをサーバーで実行する。

## 4. アーキテクチャ

**[判断]** 以下は設計者の推奨。

### 4.1 構成(compose のサービス)
- `fione`: FastAPI アプリ。Web UI の配信、API、ジョブ管理、学習サブプロセスの起動を担う 1 コンテナ。
- `seaweedfs`: S3 互換ストレージ。データセット・モデル・成果物を保存(**[ユーザー]** SeaweedFS 希望)。
- `ollama`: LLM。既定でオン(**[ユーザー]**)。
- `fione-serving`: 予測 API 用の共通イメージ(7.5 節)。compose の常駐サービスではなく、ユーザーがモデルごとに起動する。

### 4.2 ストレージとメタデータ
- オブジェクト(CSV・モデル・レポート)は S3 互換 API 経由。クライアントは `boto3` / `obstore` など。使う機能は put/get/list/delete と multipart に限定し、任意の S3 互換ストレージ(AWS S3、Ceph、他)に差し替え可能にする。
- ストレージ層は URL スキーム(`s3://` / `file://`)で切り替わる薄い抽象にする。ローカル開発やテストでは `file://`。
- メタデータ(プロジェクト、データセット、ジョブ、リーダーボード)は **SQLite** に置く(**[判断]**)。v1 の JSON ファイル群より整合性が取りやすい。SQLite ファイルへの書き込みは `fione` コンテナのみが行う。

### 4.3 ジョブ
- 学習・予測・大きなデータ処理は、`fione` コンテナが起動するサブプロセスで実行する。状態は SQLite のジョブ表(`queued/running/done/failed/cancelled`、進捗、ログ)に持つ。キャンセルはサブプロセスの終了で行う(**[判断]** Redis / Celery は使わない)。
- v1 の「作業ジョブ」(保存・削除などの短い処理)と AutoML ジョブは同じ表で扱い、UI は 1 つのジョブ画面にまとめる。

### 4.4 認証・権限
- **[ユーザー]** ユーザー認証は必要。権限・ロールは新しい設計に合わせて作り直してよい(v1 の 3 ロールには縛られない)。LDAP / OIDC は初期対象外。
- **[判断]** ロールは 3 つにする: `admin`(システム設定、ユーザー管理、モデルのインポート、モジュール・Notebook の管理)、`editor`(プロジェクトの作成・学習・予測・サービング。EasyML と AutoML 詳細の両方を使える)、`viewer`(閲覧のみ)。画面の簡易/詳細の切り替えは権限ではなく、ユーザーの表示設定とする(v1 は権限で分けていたが、使いにくさの原因になる)。
- ユーザーごとのプロジェクト分離を維持し、プロジェクト単位の共有(viewer / editor の付与)を持つ。認証はローカルユーザー(パスワードはハッシュ保存)+ API トークン。初回起動時に管理者を作成する(固定の既定パスワードは置かない)。
- 認証の差し替え点(将来の OIDC など)はインタフェースとして分けておくが、実装は初期には入れない。

### 4.6 依存ライブラリのライセンス方針
**[ユーザー]** Apache 互換のライセンスから選び、適当なものがなければ自前で作る。
- **[判断]** 許可: Apache-2.0、MIT、BSD、ISC、PSF など。禁止: GPL / LGPL / AGPL / 非商用ライセンス(例: 一部モデルプリセットの noncommercial 条項)。MPL は個別判断。
- CI で依存のライセンスを自動検査し、禁止ライセンスが入ったら失敗させる。同梱する外部サービス(SeaweedFS: Apache-2.0、Ollama: MIT)も一覧化する。
- 候補が禁止ライセンスだけの場合は自前で作る(例: gensim は LGPL と認識しているため使わない)。

### 4.5 UI
- v1 の 2 つの画面系統を維持する: **EasyML**(ウィザード形式。未経験者向け)と **AutoML**(詳細画面。専門家向け)。名称・導線はドキュメントの用語(プロジェクト、データ分析、予測する列、入力する列、最大実行時間、実行、予測結果サマリー、Fione 君)を引き継ぐ。
- **[ユーザー]** UI/UX はモダンに一新してよい。v1 の画面構成には縛られないが、ドキュメントの用語と主要な導線(アップロード → データ分析 → 実行 → 結果サマリー → 予測/Serving)は維持する。
- **[判断]** デザイン方針: 軽量なデザインシステム(CSS 変数のデザイントークン、ライト/ダーク、レスポンシブ、キーボード操作とコントラストに配慮)。重い UI フレームワークは入れない。使い勝手とわかりやすさを最優先にし、ML 未経験者向けの EasyML は 1 画面 1 目的にする。
- 技術(SPA かサーバーレンダリングか)は実装計画で決める(ビルダーに委ねる)。多言語は日英。

## 5. AutoML エンジン

### 5.1 時間予算は厳守(必須要件)
ユーザーが設定する「最大実行時間」は守られなければならない。スパイクでは超過した。要件:
- fold ごとの締め切り確認、Optuna の枝刈り、期限到達時にそれまでの最良結果を返すハード停止。
- 超過許容は予算の 5% 以内を目標とする(受け入れ基準として検証する)。

### 5.2 成果物(モデルファイル)
- 保存するのはアンサンブルで重みを持つメンバーだけ。木の大きさに上限を設ける。必要なら選択後に全データで再学習する。
- 目標: Adult 規模のデータで 100MB 以下、予測 1,000 行の遅延は 0.5 秒以内(受け入れ基準として検証する。スパイクの 761MB / 0.75 秒は不可)。

### 5.3 信頼境界(pickle)
- モデルは joblib/pickle 系になるため、ユーザーがアップロードしたファイルを読み込むと任意コード実行になる。
- 読み込むのは Fione 自身が書いた成果物のみとし、署名付きマニフェスト(HMAC)で検証する。外部モデルのインポートは管理者限定とし、警告を出す。または skops の信頼型で読み込む。

### 5.4 機能要件(v1 のパラメータ維持)
nfolds、balance_classes、seed、最大モデル数、最大実行時間、モデルごとの最大時間、停止条件(rounds / metric / tolerance)、ソート指標、CV 予測・モデル・fold 割当の保持、除外列、予測列。タスクは二値・多値分類と回帰。

### 5.5 エンジンの位置付け
**[判断]** 自作コア(LightGBM / XGBoost / CatBoost / sklearn + Optuna)を既定エンジンとする。理由: 精度が同等(2.2 節)、依存が軽い、探索の進捗・停止・説明を LLM アシストに直接渡せる、特定フレームワークへの依存を避けられる。エンジンの内部インタフェースは最小限(学習・予測・リーダーボード・キャンセル)にとどめ、AutoGluon をプラグインとして後から追加できる余地だけ残す。先回りの抽象化はしない。Python は 3.12 または 3.13 を想定(依存の対応範囲は実装時に確認)。

### 5.6 エンジンの採用ゲート
**[ユーザー]** 可能な限り自作エンジンにする。理由は、LLM アシスタントとのやりとり(探索の進捗・停止・説明の取り出し)を最適化するため。
**[判断]** スパイクの未達(時間超過・サイズ・遅延)は設計の欠陥ではなく、使い捨て実装に制御がなかったことが原因。Phase 1 の最初のトラックをエンジンとし、5.1 と 5.2 の受け入れ基準を満たすかを検証するゲートにする。AutoGluon へのラップは、基準をどうしても満たせない場合の最後の手段とし、その場合も基準自体は緩めず、ユーザーに報告して判断を仰ぐ。ゲートの結果が出るまでは、エンジン以外のトラック(UI、ジョブ、ストレージ、認証、サービング)を並行して進めてよい。
- エンジンは LLM アシスタント向けに、探索の進捗(試行ごとのスコア・パラメータ・経過時間)、停止理由、各モデルの要約、特徴量の重要度を、構造化イベントとして出力する(8・9 章のツールがこれを読む)。

### 5.7 規模と時間予算の定義
**[判断]** 以下は設計者の既定値。
- 対象は単一ホスト。数百万行・CSV で約 1GB までを想定し、アップロード時に CSV を Parquet(pyarrow)へ変換して保存する。pandas に全量を載せない処理は列統計・サンプリングで行う。
- 「最大実行時間」はジョブ全体の実時間(データ準備、探索、アンサンブル、最終再学習を含む)。5% 以内という超過の許容もこの全体で測る。
- 学習ジョブの同時実行数は既定 1(キュー待ち)。設定で変更可能。

## 6. 説明可能性・EDA(v1 以上)
- 列ごとの統計・分布(v1 同等)に加え、欠損、相関、外れ値、ターゲットリーク疑い、型の推定結果を出す。
- モデルの説明: 変数重要度、スコア履歴相当のグラフ、CV メトリクス、混同行列/残差。SHAP・部分依存は後続フェーズ。

### 6.5 Notebook 連携と Notebook 画面
**[ユーザー]** Notebook 連携があると良い。Notebook 的なものを実行する画面があるとより良い。

**[判断]** 実装方針(Phase 2 以降。Phase 1 には入れない):
- `fione-sdk`(Python パッケージ。Fione の API のクライアント)を提供する。Notebook からデータセットの取得、EDA、学習ジョブの実行、リーダーボードの参照、予測を、Fione の API 経由で行える。外部の Jupyter からも使える。
- Notebook 画面は JupyterLab(BSD-3-Clause)を compose の任意サービスとして同梱し、Fione の画面に埋め込む。自前の Notebook UI は作らない(Jupyter で足りるため)。**[ユーザー]** Fione の認証と合わせ、権限を柔軟に調整できること。
- **認証連携**(Jupyter Server の公式ドキュメントで確認済みの仕組み): `IdentityProvider` を差し替えて Fione が発行したトークンを検証し、別のログインなしで使えるようにする。`Authorizer`(`is_authorized(handler, user, action, resource)`)を差し替えて、リソース(`contents`・`kernels`・`terminals`・`sessions` など)× 操作(read / write / execute)ごとに Fione のロールとプロジェクト共有へ連動させる。例: viewer は閲覧のみ、editor は実行可、admin はターミナルも可。
- **限界**: Jupyter のドキュメントは、カーネル・ターミナルの実行権限は他の全権限と同等とみなすべきと述べている。認可では「実行できるか」しか制御できず、「何を実行するか」は制御できない。そのため権限の境界は 3 層で作る: (1) ユーザーごとの専用コンテナ(CPU・メモリ上限、外部通信の制限)、(2) コンテナ内のコードが Fione のデータ・モデルに触れられるのは、そのユーザーのトークンで `fione-sdk` を通すときだけ(トークンの権限はロールとプロジェクト共有の範囲に限る)、(3) Jupyter 側の認可(上記)。
- **起動方式**: Fione 自身がユーザーごとのコンテナを起動する方式を既定とし、JupyterHub(BSD-3)との比較は Notebook の実装時に行う(**[判断]**)。
- 既定では `admin` と明示的に許可されたユーザーだけが使える。
- 既存の Python モジュール(frame 操作・学習・予測)は、Notebook からも同じ関数で呼べるようにする。

## 8. サービング

- `/invocations`(`{"instances":[...]}` → `{"predictions":[...]}`)、`/model`、`/ping` の契約と応答形式を維持する(二値・多値は `label` / `index` / `class_probabilities`、回帰は `value`。行単位の失敗は `{"exception": msg}`)。
- v1 では SHAP を有効にしても応答に出ていなかった。**[判断]** Phase 1 の応答は v1 と同じ形にとどめ、`contributions` は SHAP を入れる Phase 2 で追加する。
- **[判断]** 「ZIP を解凍して `docker build`」をやめる。`fione` と `fione-serving` は同じロックファイルから作り、サービング用イメージはバージョン付きで共通化する。配布物は「モデルファイル + `docker run` コマンド」だけにする。バージョン固定問題も構造的になくなる。
- **[判断]** イメージの公開先は GHCR(GitHub Container Registry)とし、リリースのパイプラインで `fione` と同時に公開する。モデルファイルのマニフェストに必要なイメージのタグを記録し、一致しないイメージで起動した場合は、理由を示して起動を拒否する。
- **[判断]** 署名(HMAC)の鍵はインストールごとの鍵とし、検証は Fione 本体へのインポート時に行う。サービングは運用者が自分でデプロイするモデルを動かす前提で、署名ではなくマニフェストのハッシュ(sha256)で整合性だけを確認する。別のマシンで動かしても検証が壊れない。
- v1 の Dockerfile.serving の既知の問題(root で実行、`echo "\n"` の依存)は引き継がない。非 root で実行する。

## 9. LLM アシスタント

- **[ユーザー]** Ollama を既定でオンにし、`gemma4:12b-mlx` を使える状態にしておく前提でよい。
- 事実(ollama.com で確認): `gemma4:12b-mlx`(7.7GB)は存在する。MLX は Apple Silicon 専用。同じ 12b には `gemma4:12b`(7.7〜8.0GB)や `12b-it-q4_K_M`(8.0GB)といった非 MLX のタグもある。
- **[判断]** 既定の切り替え:
  - Mac: ホストのネイティブ Ollama に `host.docker.internal` で接続し、`gemma4:12b-mlx` を使う。
  - Linux / コンテナ内 Ollama: `gemma4:12b` 系の非 MLX タグを使う。
  - 初回起動時はモデルの取得に数 GB かかる。UI は取得中も使えるようにし、進捗を表示する。
- クライアントは OpenAI 互換 API の 1 つ(`base_url` / `api_key` / `model` を設定可能)。llama.cpp・vLLM・クラウドも同じ設定で使える。
- **ツール呼び出し方式**: LLM は型付きの読み取りツール(データ説明、列統計、リーダーボード、重要度など。10 個程度、スキーマは平坦)だけを呼ぶ。学習設定は「提案」(JSON)として返し、ユーザーが UI で確認してから実行する。LLM 生成コードはサーバーで実行しない(PandasAI の CVE-2024-12366 が反例)。
- **データの扱い**: LLM に渡すのはスキーマと統計だけ。サンプル値の送信は、プロバイダごとの明示的なオプトインにする。非ローカルの `base_url` を使う場合は常に警告を表示する。データセット由来の文字列は信頼しない入力として扱い、ツール呼び出しはログに残す。
- **既知のリスク**: Gemma 4 は思考出力が既定で有効で、ツール呼び出しが `reasoning_content` に入る可能性がある(未検証)。思考を無効にして、実機でツール呼び出しを検証する。
- ChromeのGemini Nano(Prompt API)は主経路にしない(Chrome 専用、ツール呼び出しの記載なし、文脈が小さく、数十GBのディスクが必要)。結果文の要約などで、機能検出つきの後続オプションとして検討する。
- 後続: 同じツールを MCP サーバーとして公開する(読み取り専用、既定は localhost、トークン必須。学習・削除はユーザーの明示承認)。
- Fione 君は LLM の窓口にする(v1 はチャット風表示のみ)。

## 10.5 テスト戦略
**[ユーザー]** 単体テストと E2E テストを整備する。**[判断]** 以下の構成とする。
- **単体テスト**(pytest): エンジン(前処理、探索、アンサンブル、停止、キャンセル)、ストレージ層、ジョブ表、認可、LLM のツール(スキーマ検証、データ非送出の確認)。ライブラリが乱数を使う箇所は seed を固定する。
- **エンジンの受け入れテスト**: 5.1(時間予算 +5% 以内)、5.2(サイズ・遅延)、精度(固定データセットで AutoGluon・参照値との差が許容内)を自動で検査する。実行時間が長いため、通常の CI とは分けて夜間/リリース前に走らせる。
- **API テスト**: FastAPI のテストクライアントで、全エンドポイントと権限(admin / editor / viewer)を検証する。サービングの `/invocations` / `/model` / `/ping` は v1 の応答形式を固定値で検証する(契約テスト)。
- **E2E テスト**: Playwright(Apache-2.0)で、compose を起動して主要な流れを通す(ログイン → CSV アップロード → データ分析 → 実行 → 予測結果サマリー → バッチ予測 → Serving 起動 → `/invocations`)。LLM は OpenAI 互換のスタブサーバーに差し替え、ツール呼び出しと「提案 → 確認」の流れを決定的に検証する。実際の Ollama + Gemma 4 でのツール呼び出し検証は、別の手動/夜間テストとする。
- **CI**: GitHub Actions で単体・API・ライセンス検査をプルリクエストごと、E2E は主要ブランチ、エンジン受け入れは夜間に実行する。
- Phase ごとの完了条件にテストの整備を含める(テストのない機能は完了としない)。
